# Алгоритм системы: сборка карты и рантайм-локализация

Обзор всего конвейера модуля 2 (локализация и навигация) — от видео до команды
руления. Полный проверенный конвейер построения карты описан в
`STREET_MAP_BUILDING_HANDOFF.md`, настройка команд — в
`STREET_NAVIGATION_TUNING.md`; здесь — принцип и математика целиком.

## 1. Общая схема

```
видео (перед/зад камера)
  -> нарезка кадров (фиксированный шаг)
  -> ALIKED + LightGlue (признаки и соответствия)
  -> COLMAP incremental SfM (сборка карты)
  -> очистка коротких треков -> runtime.npz + aliked_bank.npz
  -> [на роботе] ALIKED-запрос -> матчинг по банку -> PnP -> поза
  -> упреждение по задержке -> pure pursuit / Stanley -> команда
  -> DualNav (перед ведущий, зад резерв) + светофор (гейт по зоне)
  -> NATS -> мозг
```

Две независимые математические задачи: **офлайн** — восстановить 3D-геометрию
маршрута с единым масштабом (SfM); **онлайн** — по одному кадру найти позу
камеры относительно уже готовой геометрии (PnP) и превратить её в руль.

## 2. Сборка карты

### 2.1 Нарезка кадров

Раньше нарезка была адаптивной — по optical flow (Lucas-Kanade, сетка точек,
forward-backward проверка), кадр сохранялся при накоплении сдвига картинки.
Это оказалось **источником главной проблемы дня**: на поворотах вращение
камеры (yaw) создаёт большой пиксельный flow без полезной трансляционной
базы — algorithm принимал вращение за параллакс и держал до 15 кадров/с с
почти нулевой базой. Именно нулевая база на поворотах давала схлопывание
масштаба ("матрёшку") при последующей SfM.

Исправление: **равномерный шаг по исходному видео** (`--fixed-gap 8` при
30 fps ≈ 3.75 fps), не зависящий от flow. Стоянки всё ещё исключаются:
кадр не берётся, пока не накопится заметное смещение относительно последнего
сохранённого (иначе стоячие кадры дают ту же нулевую базу).

### 2.2 Признаки и соответствия

ALIKED (детектор+дескриптор, обучаемая сеть) извлекает ключевые точки на
каждом кадре. LightGlue сопоставляет их между парами кадров (последовательные
пары, `overlap=25` — то есть каждый кадр сравнивается с 25 следующими).
Признаки и матчи считаются **один раз** и складываются в `database.db`
(SQLite, формат COLMAP) — дорогая операция, переиспользуется на всех
последующих попытках реконструкции.

### 2.3 Реконструкция (COLMAP incremental)

Инкрементальная SfM: кадры регистрируются по одному через PnP относительно
уже восстановленных 3D-точек, затем локальный и периодический глобальный
bundle adjustment (BA) пересчитывает позы и точки совместно, минимизируя
суммарную ошибку репроекции:

```
min Σ ||π(K, R_i, t_i, X_j) - x_ij||²
```

по всем позам камер `(R_i, t_i)`, точкам `X_j` и (опционально) интринсикам
`K`, где `π` — проекция точки на кадр, `x_ij` — измеренная 2D-позиция.

Ключевое решение состоит из двух стадий. На коротком устойчивом якоре
интринсики разрешено уточнить; для передней камеры маршрута 1–2 GLOMAP оценил
модель `FULL_OPENCV`. После визуального и численного принятия якоря параметры
камеры **фиксируются**, а COLMAP расширяет эту же связную реконструкцию с
локальной и периодической глобальной BA поз и 3D-точек. На длинном
слабопараллаксном участке повторное уточнение focal/distortion опасно: глубина и
дисторсия могут компенсировать друг друга.

Фиксировать интринсики на грубой догадке (например, автоматически полученных
1536 px) тоже нельзя: сначала нужна устойчивая оценка камеры. Отдельно испытанная
жёсткая фиксация всех старых поз с добавлением по 1/10 камер не переносила
локальный масштаб и была отклонена. Проверенная схема — принятый якорь,
фиксированные интринсики, расширения примерно по 200 кадров и настоящая BA всей
связной модели с численным Sim(3)-контролем общей части.

### 2.4 Очистка и экспорт

Из полной реконструкции строится отдельная **runtime-копия**: удаляются
3D-точки с длиной трека меньше 3 (шумные, единично видимые точки), но не
агрессивнее — на слабых уличных участках короткие треки всё ещё полезны.
Экспорт (`export_map.py`) достаёт из COLMAP-модели:

- `pos[i]`, `fwd[i]` — позиция и направление взгляда каждого узла маршрута
  (камеры вдоль пройденного пути становятся узлами эталона для руления);
- `K`, `dist`, `size` — интринсики и разрешение;
- `points` — облако 3D-точек;
- `align` — поворот вокруг вертикали, чтобы старт/финиш карты стабильно
  смотрели вверх на визуализации (чисто косметика для viz).

Экспортёр сохраняет как обычную `OPENCV`, так и `FULL_OPENCV`. Для
`FULL_OPENCV` в `dist` записываются все восемь коэффициентов rational-модели в
порядке OpenCV: `k1,k2,p1,p2,k3,k4,k5,k6`; PnP использует их без усечения.

Отдельно строится **банк дескрипторов** (`aliked_bank.npz`): для каждой
3D-точки берётся до 12 её дескрипторов из разных кадров, где она видна
(track), с меткой `owner` — индексом точки. Банк — это то, с чем матчится
живой кадр в рантайме; чем он больше, тем дороже матчинг (см. §3.2).

## 3. Рантайм-локализация

### 3.1 Извлечение признаков запроса

Тот же ALIKED (fp16 на GPU) извлекает ключевые точки текущего кадра камеры.
Стоимость не зависит от размера карты — фиксированный прогон сети.

### 3.2 Матчинг по банку

Для каждой query-точки ищется лучшее совпадение среди дескрипторов банка —
косинусное сходство `sim = q · mᵀ` (батчами/чанками по памяти). На точку
берутся top-k кандидатов, отслеживаются **лучший и второй-лучший результат
по разным 3D-точкам** (не по сырым дескрипторам — у одной точки может быть
до 12 дескрипторов, они не должны конкурировать друг с другом как
"первый/второй"). Тест Лоу на псевдо-расстоянии, полученном из косинуса:

```
d = √(2 − 2·sim)         (хордовое расстояние на единичной сфере)
keep = (d₁ / d₂) < MATCH_RATIO
```

**Оконный матчинг:** если известен узел из прошлого кадра, банк заранее
режется до дескрипторов точек в диапазоне `[last_node − WIN, last_node +
WIN]` (`NAV_WIN_NODES`, ±узлов). Матчинг растёт линейно с размером банка,
поэтому окно — прямой рычаг скорости на больших картах; при потере
локализации или на старте окно снимается (матчим по всему банку, пока не
найдёмся заново).

### 3.3 PnP — поза по 2D-3D

Из выживших пар (2D keypoint, 3D точка) — `cv2.solvePnPRansac` (EPnP) +
`solvePnPRefineLM` по инлайерам. Возвращает `R, t`; позиция и направление
камеры в мировых координатах:

```
C   = −Rᵀ t                    (центр камеры)
fwd = Rᵀ · [0, 0, 1]ᵀ           (оптическая ось в мировых координатах)
```

Если камера смотрит назад по ходу движения (`CAMERA_BACK`), `fwd`
инвертируется — команды руления должны считаться в системе робота, а не
камеры.

### 3.4 Компенсация задержки (упреждение)

Между съёмкой кадра и исполнением команды проходит время `t_ext + t_match +
t_pnp` (+доставка). Чтобы робот не запаздывал на поворотах, точка, из
которой считается руление, сдвигается вперёд по курсу на пройденное за это
время расстояние:

```
v     = ‖C − C₀‖ / Δt                    (скорость по сглаженной истории поз)
lead  = min(v · LAG_S, LEAD_MAX)         (потолок — защита от выброса скорости)
C_lead = C + lead · f̂
```

Только точка старта луча сдвигается — сам маршрут (цель прицеливания) не
трогается.

### 3.5 Руление

Ближайший узел ищется **с фильтром по курсу** (`route_fwd · f̂ >
HEADING_GATE`) — иначе на пересекающемся/петляющем маршруте робот может
зацепиться за встречный проход того же места. Боковое отклонение от линии —
знаковое:

```
e = (t̂ × v) · down,   v = C − route[k], down = [0,1,0]
```

(положительное — правее линии). Дальше два закона:

**Pure pursuit** (по умолчанию) — целимся в точку впереди по длине дуги, не
по числу узлов (узлы неравномерно расставлены после fixed-gap нарезки).
Упреждение адаптивно сокращается при отклонении от линии:

```
want = max(LOOKAHEAD_NODES − LOOKAHEAD_ADAPT · |e|, LOOKAHEAD_MIN) · node_step
j    = searchsorted(route_cum, route_cum[k] + want)
ang  = atan2( (f̂ × to)·down, f̂ · to ),   to = route[j] − C
```

**Stanley** (альтернатива) — угол курса к касательной эталона + поправка на
поперечное смещение: `ang = ψ + atan(−k·e)`.

Дальше — мёртвая зона (`|ang| < DEADZONE_DEG` → `straight`) и защёлка стопа
у конца маршрута (ближайший узел в последних `STOP_END_NODES` → `stop`).

### 3.6 Приём фиксов (Pilot)

Между сырым результатом локализации и командой в NATS стоит `Pilot`:
отбрасывает скачки узла быстрее физически возможного (`MAX_NODES_PER_SEC`),
держит последнюю команду при неподвижности (пока не сдвинулся сам узел —
это тоже считается движением, иначе плотная карта могла давать ложное
"стоим"), защёлкивает `stop` после нескольких уверенных стоп-фиксов подряд,
поддерживает `pause`/`resume`/`reset` от админки.

## 4. Двухкамерная навигация (DualNav)

Передняя и задняя камеры — **два независимых локализатора** на своих
картах, без общей системы координат в рантайме (в отличие от карт, которым
единый масштаб нужен математически, для руления общая система не нужна —
достаточно, что обе карты дают согласованные по знаку команды). Гистерезис
переключения:

- ведёт фронт; после `DUAL_LOST_HOLD` потерь подряд активной становится
  задняя;
- ведёт зад; после `DUAL_BACK_HOLD` удачных фронт-фиксов подряд —
  возврат на переднюю.

Задняя камера считается **лениво** — только когда она реально ведёт, чтобы
не удваивать время кадра на слабом железе.
